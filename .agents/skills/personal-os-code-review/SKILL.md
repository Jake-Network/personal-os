# Personal OS 코드 리뷰

원본의 요구사항·규칙 두 축을 유지하고 미커밋 변경, 재현 근거, 위험도를 추가했다. 루트 `AGENTS.md`와 대상 영역의 지침을 우선한다. 리뷰만 요청받으면 읽기 전용으로 진행한다. 구현 후 자체 검토는 승인된 변경 범위의 유효한 문제를 수정하고 다시 검증한다. 원본 저작권은 [MIT 라이선스](../LICENSE.mattpocock)에 보존한다.

## 리뷰 범위를 먼저 고정

- `git status --short`로 기존 변경을 확인한다. 사용자가 준 PR·기준 ref가 있으면 SHA로 고정하고 대상 HEAD SHA와 함께 기록한다. PR 리뷰는 가능한 경우 대상 ref를 격리한 checkout에서 진행하며 현재 작업트리를 checkout·reset·stash하지 않는다.
- 브랜치 변경은 `git diff <base-sha>...<head-sha>`와 해당 커밋 목록을 본다. 로컬 변경 리뷰는 `git diff HEAD -- <대상 경로>`와 `git ls-files --others --exclude-standard`의 관련 신규 파일을 함께 읽는다. staged·unstaged를 나눠 볼 때는 `git diff --cached`와 `git diff`를 모두 확인한다.
- 구현 후 자체 검토는 작업 시작 시 확인한 diff·경로와 비교해 이번 변경을 구분한다. 관련 없는 기존 변경은 수정하지 않는다. 대상이 명확하면 기준점을 다시 묻지 않고 선택한 범위를 밝힌다. diff가 비었더라도 관련 신규 파일 확인 전에는 변경 없음으로 결론 내리지 않는다.
- 요구사항은 현재 사용자 요청, 제공된 spec·issue, 기존 계약 순으로 찾는다. issue가 없다는 이유로 tracker 설정이나 새 문서 작성을 요구하지 않는다. 찾지 못한 요구사항은 검토 한계로 표시한다.

## 두 축을 독립적으로 검토

독립 검토가 도움이 될 크기라면 네이티브 서브에이전트에 같은 고정 범위·요구사항·지침 경로를 전달해 두 축을 병렬 검토한다. 읽기 권한과 각 책임을 명시한다. 작거나 위임할 수 없는 작업은 두 축을 별도로 검토하고 독립 검토를 수행했다고 주장하지 않는다.

**요구 동작:** 요청한 사용자 동작의 누락·오구현, 예상하지 않은 부작용과 범위 확장을 찾는다. 변경 함수에서 호출자·저장·외부 전송·사용자 출력까지 따라가고 실패·재시도·경합 등 관련 반례를 확인한다.

**프로젝트 규칙:** 적용되는 `AGENTS.md`, 기존 계약·스키마·테스트와 비교한다. 아래에서 해당 영역만 선택한다.

- 개인정보·문서: 공유 해제 후 과거 이력·파생 근거도 차단되는지, 실제 outbound payload와 인용 버전·삭제 범위가 맞는지.
- 재무·DB: Decimal·누락 플래그·과거 이력 출처, append-only·버전 검사, 모델과 Alembic revision, 기존 데이터 업그레이드, 세션·commit 소유권.
- 상담 실행·승인: lease·generation·checkpoint 쓰기 권한, 중복 실행·승인, 외부 호출 불확실성, 스트림 중단 이력과 구독·실행 수명의 구분.
- 프런트엔드·API: OpenAPI·Orval 원본 계약, 공용 전송·오류 처리, Query 무효화, 한국어 상태·접근성, 실제 브라우저 검증 여부.
- 연결·신뢰: 계정 전환·암호화·Origin/Host, 명시적 제공자 선택, 웹 검색 공개 검색어·수집 경계. 제품 승인 절차가 개발 에이전트의 자율성 때문에 생략되지 않는지.

중복·복잡성·얕은 위임 같은 설계 지적은 구체적인 변경 비용이나 실패 가능성으로 뒷받침한다. lint가 처리하는 스타일이나 취향을 기능 결함과 같은 수준으로 올리지 않는다. 단순 위임이라도 권한·트랜잭션·정책 경계의 역할을 먼저 확인한다.

## 근거와 보고

의심되는 문제는 파일·라인과 실제 도달 조건을 확인하고 가장 작은 안전한 검사로 재현한다. 테스트 환경은 폐기용 DB와 합성 데이터를 사용한다. 코드로 확인한 사실, 실행 재현, 추정과 환경 제약을 구분한다.

결과는 심각도 순으로 정리하되 각 finding에 `요구 동작` 또는 `프로젝트 규칙` 축을 표시한다. 발생 조건 → 사용자 영향 → 파일·라인 → 근거 → 최소 수정 방향을 담는다. 실행한 검사와 미실행·skip 검사는 별도로 밝힌다. PR 리뷰에는 병합 권고를, 자체 검토에는 수정한 문제와 남은 문제를 보고한다. 문제가 없으면 검토 범위와 검증 한계를 짧게 남긴다. 커밋·푸시·병합은 요청된 범위만 수행한다.
